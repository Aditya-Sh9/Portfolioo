<CaseSection index="01" title={sections[0].title}>

SOLACE is an emotionally intelligent AI wellness companion. It’s not a medical app and it’s not a chatbot — it’s built to feel like a personal health detective with a warm, human soul: something that helps you notice the quiet, hard-to-name things (low energy, brain fog, mood swings, “just off”) and surfaces honest, non-clinical patterns in your own data, without ever diagnosing or prescribing.

It’s a solo portfolio project, built in public phases, and it’s in active development: Phases 0–4 are complete and Phase 5 is in progress.

### Why I built it

I wanted to explore how AI could be used for wellness without turning into another generic chatbot. The idea came from noticing how difficult it can be to connect things like sleep, stress, energy, mood, and lifestyle into a bigger picture, so I built SOLACE around finding those patterns while keeping the experience non-clinical and human.

### Who it’s for

People who feel that something is “off” but cannot easily explain why, especially students and young professionals dealing with stress, inconsistent routines, and generic wellness advice.

### My role

I designed and built SOLACE end-to-end, including the product flow, architecture, backend/ML separation, data model, AI pipeline, and frontend experience. The hand-drawn visual language was also intentionally designed as part of the product identity, with customized UI components rather than using a generic template.

- The frontend never talks to the database, Gemini, or the ML service directly — everything routes through the backend.
- `GET /api/patterns` is decoupled from the main dashboard load and has a 4-second timeout: if the ML service is slow, asleep, or fails, the prediction card is silently hidden rather than blocking the dashboard.
- The journal (Phase 5) is encrypted in the browser using Web Crypto: the key never leaves the client, and the backend stores only ciphertext.

<Note>The backend and ML service run on Railway’s free tier, which sleeps after inactivity — the first request after a while may take a few seconds to wake up.</Note>

<CaseSection index="05" title={sections[4].title} layout="wide">

<DecisionGrid>
  <Decision
    n="01"
    title="A separate Python ML service"
    why="Python has a much stronger ML ecosystem through libraries like scikit-learn, while TypeScript is better suited to the application’s API and business logic. Keeping it separate also gives the ML layer its own deployment and scaling boundary, while preventing the frontend from ever accessing the ML service directly."
    tradeoff="It adds another service to develop, deploy, monitor, and communicate with, but the separation gives me cleaner responsibilities and makes the architecture easier to evolve."
  />
  <Decision
    n="02"
    title="A stateless model, retrained per request"
    why="The backend sends the user’s complete check-in history to the ML service, which trains the Gradient Boosting models in memory for that request and immediately returns the prediction. This avoids storing model files on Railway’s ephemeral filesystem and keeps the service horizontally scalable."
    tradeoff="The model has to retrain for every prediction request, so there is some additional CPU/time cost compared with loading a persisted model. With the current small per-user datasets, the training is lightweight enough that the simplicity and reliability are worth it."
  />
  <Decision
    n="03"
    title="Rule engine decides, Gemini writes"
    why="The rule engine is responsible for the deterministic wellness signals/flags, while Gemini turns those signals into warm, human-readable insight copy. This keeps the important decision logic deterministic and testable instead of asking an LLM to independently decide whether a user has a particular signal."
    tradeoff="It requires maintaining two layers instead of letting one AI model do everything, but it gives much better control, testability, and consistency."
  />
  <Decision
    n="04"
    title="Gemini Flash"
    why="SOLACE needs fast, lightweight text generation rather than a large reasoning model. It is used mainly for synthesizing already-structured signals into concise, warm insight cards, so a faster model with low inference cost was a better fit. The implementation also includes rate limiting, caching/storage of generated insights, and fallback copy when Gemini is unavailable."
  />
  <Decision
    n="05"
    title="Supabase with Prisma"
    why="Supabase gives me managed PostgreSQL plus authentication, while Prisma gives the backend a type-safe ORM and migration workflow. Supabase handles infrastructure/auth while the Express backend retains ownership of database access, instead of allowing the frontend to directly query application data."
  />
  <Decision
    n="06"
    title="A 14-check-in gate and confidence checks"
    why="The model is learning an individual’s patterns rather than using a large population dataset, so below fourteen check-ins there simply isn’t enough personal history to justify a prediction. After training, confidence combines sample count, cross-validation stability, correlation agreement, and model variance; the prediction is also hidden on negative R², degenerate output variance, or unstable correlation patterns across bootstrap resamples."
  />
</DecisionGrid>

</CaseSection>

### Testing

- **89 backend tests (Vitest)** cover the rule engine, the Gemini tone validator and the ML client.
- **60 ML-service tests (pytest)** cover feature preparation and the model’s training, sanity, stability and confidence gates.

### Rule engine

Nine rules: five deficiency-related rules (iron, vitamin D, magnesium, B12, vitamin C), three lifestyle rules (sleep debt, dehydration, sedentary behaviour) and one sustained-stress rule. The rules are based on peer-reviewed nutritional science, with their sources documented in the project.

### Security and safety

- Supabase authentication with session verification on API routes.
- Zod validation at API boundaries, and Prisma parameterized queries.
- Rate limiting, sanitized markdown, and environment-variable separation.
- Gemini is kept behind the backend rather than being exposed directly to the frontend.
